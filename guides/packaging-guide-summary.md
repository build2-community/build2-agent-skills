# build2 Packaging Guide

## Overview

This guide covers converting third-party C/C++ projects to the `build2` build
system and making them available as packages from `cppget.org`, the `build2`
community's central package repository.

A `build2`-based project can only consume packages that use the `build2` build
system. There is no support for wrapping or otherwise adapting third-party
projects' existing build systems. The build system must be replaced. This
requires more work upfront but the long-term maintenance benefits are well
justified.

The guide focuses on libraries as the baseline (libraries are more complex than
executables and are the strong majority of packages on `cppget.org`). Most
library-specific steps are easily identified and can be skipped when packaging
an executable.


## Concepts

**Upstream.** The third-party project and its authors. "Upstream source code"
refers to the C/C++ source files. "Upstream build system" refers to the
`CMakeLists.txt`, Meson files, or other build definitions upstream already has.

**Package git repository.** The `git` repository that hosts the `build2`
packaging work for the upstream project. Third-party packages are hosted under
`https://github.com/build2-packaging`.

**Multi-package repository.** A single `git` repository that contains more
than one `build2` package subdirectory. This is the recommended setup even for
projects that start with a single package, since it allows adding more packages
later without major restructuring.

**Git submodule pattern.** The upstream repository is imported as a `git`
submodule in the `upstream/` subdirectory of the package repository. Symlinks
from the package directory tree point into `upstream/` to non-invasively
overlay `build2` build files over the upstream source code. This pattern keeps
upstream source code unmodified and makes updating to a new upstream release
straightforward.

**Continuous versioning.** While packaging work is in progress, the package
version is kept at a pre-release snapshot form such as `2.1.0-a.0.z`. This
ensures every commit in the repository has a unique, monotonically increasing
version. When the package is ready to release, [`bdep release`](../bdep/bdep-release.md) stamps the final
version.

**Version revisions.** After releasing a version such as `2.1.0`, small fixes
to the packaging infrastructure are released as revisions (`2.1.0+1`,
`2.1.0+2`, etc.). The major/minor/patch components change only in response to
upstream releases.


## Packaging Workflow Checklist

1. Check whether a package repository already exists.
2. Create the package `git` repository in your personal workspace.
3. Initialize the repository with [`bdep new`](../bdep/bdep-new.md) `--type empty,third-party`.
4. Add the upstream repository as a `git` submodule at `upstream/`.
5. Decide on the package name and source code layout.
6. Generate the `buildfile` templates with `bdep new --package`.
7. Adjust the package version to the pre-release snapshot form.
8. Initialize the package in one or more build configurations with [`bdep init`](../bdep/bdep-init.md).
9. Add dependencies to `manifest` and `repositories.manifest`.
10. Fill the package with upstream source code using symlinks.
11. Adjust project-wide build system files in `build/`.
12. Adjust source subdirectory `buildfiles` (header buildfile, source buildfile).
13. Build and test the library or executable build in isolation.
14. Write a smoke test under `tests/`.
15. Test locally, including the installed case and source distribution.
16. Commit and submit to the CI service with [`bdep ci`](../bdep/bdep-ci.md).
17. Replace the smoke test with upstream tests (if applicable).
18. Adjust the root `buildfile` and `manifest`.
19. Adjust `PACKAGE-README.md` and the repository `README.md`.
20. Transfer the repository to `github.com/build2-packaging`.
21. Release the final version with [`bdep release`](../bdep/bdep-release.md) `--no-open`.
22. Publish to `cppget.org` with [`bdep publish`](../bdep/bdep-publish.md).


## Step 1: Set Up the Package Repository

Check these locations before starting, in case work already exists:
- `cppget.org` -- published packages
- `queue.cppget.org` -- submitted but not yet published
- `github.com/build2-packaging` -- all third-party package repositories
- `github.com/build2-packaging/WISHLIST` -- wishlist issues

Create a new empty public `git` repository in your personal workspace. Set the
description to `build2 package for <name>`. Do not add any files automatically.
Clone it using SSH.

Initialize with `bdep new`:

```
$ cd foo/
$ bdep new --type empty,third-party
$ git add .
$ git commit -m "Initialize package repository"
```

This creates `README.md`, `repositories.manifest`, `.gitattributes`, and
`.gitignore`. The first commit must contain only files generated by `bdep new`
with no manual changes, as the review process relies on this.

Add the upstream repository as a `git` submodule and point it to the release
commit:

```
$ git submodule add https://github.com/<upstream>/foo.git upstream
$ cd upstream/
$ git checkout vX.Y.Z
$ cd ../
$ git add .
$ git commit -m "Add upstream submodule, vX.Y.Z"
```

Use `https://` for the submodule URL. Never use a URL requiring authentication.


## Step 2: Determine Package Structure

**Repository name.** Use the upstream repository name as the package repository
name. No `build2-` prefix or `-package` suffix.

**Package name for executables.** Use the upstream name unless there is a good
reason to deviate. Check Debian for guidance.

**Package name for libraries.** Prefer the `lib` prefix to distinguish from
executables and avoid future name clashes. This is a recommendation, not a hard
requirement, unless an executable of the same name exists. When in doubt, add
the prefix.

**Single vs. multi-package.** If upstream provides both a library and an
executable, split them into separate `build2` packages. Use a multi-package
repository setup in either case. Never bundle an executable and a public
library in a single package since they require different dependency types.

**Source code layout.** Stay as close to upstream layout as possible. Deviating
makes it harder for upstream to adopt `build2` and more likely to cause
compile errors due to header inclusion paths.

Key information to gather by studying upstream:
- How are public headers included? (with a subdirectory prefix such as
  `<foo/util.hpp>`, or with the library name in the filename such as
  `<foo-util.hpp>`)
- Are public headers and source files split into separate directories?
- What is the installation location of public headers?

Use `bdep new --package` with sub-options to generate a layout that matches
upstream. Iterate until satisfied, deleting and re-running rather than manually
editing, since the generated templates have years of refinement.

Common `bdep new` sub-options:
- `split` -- separate `include/` and `src/` directories
- `subdir=foo` -- source subdirectory named `foo/`
- `no-subdir-source` -- no source subdirectory inside `src/`
- `no-version` -- omit the auto-generated version header
- `no-symexport` -- upstream provides its own symbol export mechanism
- `auto-symexport` -- enable automatic DLL symbol exporting
- `binless` -- header-only library
- `buildfile-in-prefix` -- place `buildfiles` in the prefix rather than the
  source subdirectory, enabling symlinking of entire directories
- `third-party` -- sets `no-version`, `no-symexport`, and adds packaging
  metadata fields to `manifest`

Example for a split layout:

```
$ bdep new --package \
  --lang c++,cpp \
  --type lib,split,subdir=foo,no-subdir-source,third-party \
  libfoo
```


## Step 3: Write the Package Manifest

The `manifest` file is in the package root directory. Key fields:

```
: 1
name: libfoo
version: 2.1.0-a.0.z
language: c++
project: foo
summary: C++ library implementing secure Foo protocol
license: MIT
description-file: README.md
package-description-file: PACKAGE-README.md
changes-file: NEWS
url: https://example.org/upstream
email: upstream@example.org
package-url: https://github.com/build2-packaging/foo
package-email: packaging@build2.org
depends: * build2 >= 0.16.0
depends: * bpkg >= 0.16.0
```

**version.** Start with the pre-release snapshot form `X.Y.Z-a.0.z` during
packaging. Run `bdep release --no-open` when ready to publish.

**summary.** Under 70 characters. No weasel words ("modern", "fast", etc.).
Do not capitalize subsequent words unless proper nouns. No trailing period.
Recommended template: `<functionality> C++ library`.

**license.** Use the SPDX license identifier. See
`https://spdx.org/licenses/` for the full list.

**depends.** Use the `^` constraint operator for semver dependencies. For
dependencies within the same repository, use `== $` to require the same version.

Optional but useful fields: `topics`, `doc-url`, `src-url`, `builds`
(to restrict CI configurations).

For the complete field reference, see
[bpkg manifest reference](../bpkg/bpkg-manifest-reference.md).


## Step 4: Write the Root Buildfile

The root `buildfile` pulls in subdirectories and lists root-level files. A
typical generated root `buildfile` for a library looks like:

```
./: {*/ -build/}                          \
    doc{README.md PACKAGE-README.md NEWS} \
    legal{LICENSE} manifest

# Don't install tests.
#
tests/: install = false
```

Adjust as needed:
- If upstream has a `docs/` subdirectory, symlink it and list files using the
  `doc{}` target type. Exclude it from the wildcard with `-docs/` if it
  contains a separate `buildfile`.
- If the executable has a man page, list it with `man1{foo}`.
- Do not list an `INSTALL` file since `PACKAGE-README.md` serves that purpose.
- Do not build main targets (libraries, executables) in the root `buildfile`.
  Instead keep them in a subdirectory `buildfile`. Loading the root `buildfile`
  during target importation would otherwise wastefully load all subprojects.


## Step 5: Write Source Buildfiles

After symlinking upstream source files into the package tree, adjust the
generated `buildfiles`.

**project-wide files in `build/`:**
- `bootstrap.build` -- specifies the project name and loads core modules.
  Rarely needs changing.
- `root.build` -- project-wide settings. Add additional module loads here
  (e.g., for Objective-C, Assembler). Declare `config.*` variables for
  optional upstream features.
- `export.build` -- export stub for target importation. Rarely needs changing.

**header `buildfile` (`include/foo/buildfile`).** Controls header installation.
The primary change is adjusting the `install` path:

```
# Install into the foo/ subdirectory of, say, /usr/include/
{hxx ixx txx}{*}:
{
  install         = include/foo/
  install.subdirs = true
}
```

If headers are included without a subdirectory prefix (e.g., `<foo-util.hpp>`),
install directly into `include/` instead.

**source `buildfile` (`src/buildfile`).** This file defines the library target,
lists sources, handles dependencies, and sets build and export options.

Listing sources and excluding files:

```
# All private headers and sources.
lib{foo}: {hxx cxx}{**} $impl_libs $intf_libs

# Exclude platform-specific files and use conditional includes instead.
lib{foo}: {hxx cxx}{** -impl-win32 -impl-posix}
lib{foo}: cxx{impl-win32}: include = ($cxx.target.class == 'windows')
lib{foo}: cxx{impl-posix}: include = ($cxx.target.class != 'windows')
lib{foo}: $impl_libs $intf_libs
```

Build and export options. Always append (`+=`) to `*.poptions`, `*.coptions`,
`*.libs`, etc. rather than assigning, since the user may have pre-populated
them. Export options (`*.export.*`) are assigned:

```
cxx.poptions =+ "-I$src_pfx_src" "-I$src_pfx_inc"

if ($cxx.target.class == 'windows')
  cxx.poptions += -DFOO_WIN32
else
  cxx.poptions += -DFOO_POSIX

lib{foo}:
{
  cxx.export.poptions = "-I$src_pfx_inc"
  cxx.export.libs = $intf_libs
}
```

Compile/link option variables and their rough `make` equivalents:

```
*.poptions   preprocess        CPPFLAGS
*.coptions   compile           CFLAGS/CXXFLAGS
*.loptions   link              LDFLAGS
*.aoptions   archive           ARFLAGS
*.libs       system libraries  LIBS/LDLIBS
```

System libraries (such as `-lm`, `-ldl`, `ws2_32.lib`) go in `c.libs` or
`cxx.libs`, not as imported targets.

Shared library ABI versioning uses `bin.lib.version`. The generated default
embeds major and minor version in the binary name, treating only patch releases
as ABI-compatible.

For extra requirements (Objective-C, Assembler, `.in` template processing,
`config.h.in` with Autoconf probing, unit tests in the source directory,
source code generators), see the build system manual and the `build2` HOWTO.


## Step 6: Handle Dependencies

**Identifying dependencies.** Check upstream documentation and the existing
build system. Look for bundled (vendored) dependencies inside the upstream
repository. These must be unbundled: express them as proper external package
dependencies instead. Bundled testing frameworks (especially `catch2`) are
particularly common.

**Adding to `repositories.manifest`.** Uncomment the `cppget.org` prerequisite
entry and set the `location` to the least stable section that contains all
required dependency versions (`stable` < `testing` < `beta` < `alpha`):

```
:
role: prerequisite
location: https://pkg.cppget.org/1/stable
```

**Adding to `manifest`.** Add one `depends` line per dependency. Use `^` for
semver dependencies:

```
depends: libz ^1.2.0
depends: libasio ^1.28.0
depends: libsqlite3 ^3.39.4
```

For a co-located package in the same repository, use `== $`:

```
depends: libfoo == $
```

**Synchronize build configurations** after editing `manifest` ([`bdep sync`](../bdep/bdep-sync.md)):

```
$ bdep sync -a
```

**Interface vs. implementation dependencies.** In library `buildfiles`, import
dependencies into `intf_libs` if the dependency's headers appear in the
library's own public headers (the dependency becomes part of the library's
interface). Otherwise import into `impl_libs`:

```
import intf_libs = libasio%lib{asio}
import impl_libs = libz%lib{z}
import impl_libs += libsqlite3%lib{sqlite3}
```

Export interface dependencies via `cxx.export.libs`:

```
lib{foo}:
{
  cxx.export.poptions = "-I$src_pfx_inc"
  cxx.export.libs = $intf_libs
}
```

For executable dependencies there is no interface/implementation distinction.
All go into a single `libs` variable.


## Step 7: Configure Installation

Public header installation is controlled in the header `buildfile` using the
`install` and `install.subdirs` target-specific variables.

The `install` module is loaded by default in `build2`-generated projects. The
`config.install.root` variable sets the installation prefix (e.g.,
`config.install.root=/usr`). Standard sub-paths are `include/`, `lib/`,
`bin/`, `share/doc/<name>/`, etc.

For libraries with an extra installation subdirectory (e.g., for versioned
side-by-side installs at `include/foo-v2/foo/`), specify the extra search path
in the generated `pkg-config` files using `cxx.pkgconfig.include`:

```
lib{foo}: cxx.pkgconfig.include = include/"foo-v$version.major"/
```

For libraries with generically named headers that must be installed into a
subdirectory for co-existence, add the unqualified search path only to build
options (not export options) so the library's own source can find the headers,
while consumers use the qualified path.

Test installation into a temporary directory to verify header placement:

```
$ rm -rf /tmp/install
$ b install config.install.root=/tmp/install
```
